待办页终于能出队

「把不知道变成可处理的队列」是这一页存在的理由（DESIGN 附录四 §2）。 0.6.0 之前它只能入队：问题答了也划不掉，缺口解了还堆在那儿， 想改只能重跑一次完整的复盘导入。

现在能就地结案，也能撤销：

  • 未答问题 → 记下答案 / 作废；已答的可以退回未答
  • 未解缺口 → 标记已解（六项受控词表 + 答案 + 日期）；已解的可以退回未解
  • 两个新端点 POST /api/question、POST /api/gap

分工一句话说得清：创建归复盘，结案归网页。题面、起因、关联的工单与部件 仍然只能走 import.py，网页递过去一律 400 并告诉你该走哪个入口。

「自己推的」标完仍然留在未解列表里

这是 DESIGN §2 的冻结判定，本次没改：resolution 选 inferred 时 resolved=1 也照样算未解。UI 会在你选中它的那一刻就说明这件事—— 不说的话，点完看到它还在列表里，只会以为按钮坏了。

下拉不给默认值。在一套「自己推的不算数」的系统里，把答案来源默认成最强的 那一档（「问了师傅」）是最不该做的事。

顺带堵掉一条真实的数据丢失路径

import.py 原先按日期无条件整片删 question 与 learning_gap， 不管 JSON 里有没有带这两批内容。开出结案入口之后，这就成了：

> 早上在待办页标了「已答」，晚上导入一份只写 learnings 的复盘 —— 早上标的没了。

这正是 0.4.0 为 work_segment 修过的同一个缺陷，修法照搬：复盘明确带了 questions / learning_gaps 才整片替换（那等于你主动重述当天的内容）， 没带就一个字节不动。

--dry-run 的预览跟着修好。不改的话，不带 questions 的导入会把现有条目 预告成「替换 → 0」——方向最坏的一种错：它告诉你会丢数据，而这条改动的核心 保证恰恰是不会丢。现在它如实显示「保留」。

备份分窗口

待办结案走独立的 hvac-log-todo-<时间戳>.db，最近 10 份，不与日历的 hvac-log-day-* 互挤。理由和 0.4.0 分出 day 窗口时一样：频率不同的操作 共用一个窗口时，高频的会把低频的快照挤出去。

顺带修好的两处

- _translate 的兜底原先匹配「任何 CHECK 约束失败」并返回一句日薪提示， 于是别的表违约都会收到完全无关的话——日历页的 seg_type 写错就会触发。 - README 的「八个页面」是 0.5.0 加第 9 个 tab 时漏改的。
