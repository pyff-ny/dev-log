撤销不再是一道记忆力测验

0.6.0 的两个待办结案端点是整块替换：payload 里没传的字段一律置 NULL。 代价藏在「撤销」上——要撤销，调用方必须自己重建一份改之前的完整快照回传， 记漏一个字段就等于删数据。

CASE-2026-107 在 Stage 2b 做了三轮独立只读评审，每轮都抓到东西， 三个缺陷全部落在 static/app.js，而且全是同一件事的变体：

1. 「退回未解」只发 {gap_id, resolved: 0}，把 learning_gap.answer 一并清空 ——那是「当时的答案」，未解状态下合法且由 import.py 写。网页删掉了复盘写的数据。 2. 改成回传整块之后，遇到 import.py 写得出的 resolved=0 且 resolution 非空的行，原样回传会被写端点自己的校验拒掉，而撤销跑在 toast 回调里没人接住。 3. 400 文案还在教人用那份会丢数据的 payload。

0.7.0 把「还原到先前状态」的正确性从调用方收回服务端：

``` 键缺席 →「没提到」，不写该列 键在场为 null →「想清空」，写 NULL 键在场有值 →「改成这个」，校验后写入 键在场且非法 → 400，一条没放宽

不变量优先于「缺席不写」： status='open' ⇒ 清答案三件套 resolved=0 ⇒ 清 resolution / resolved_date 而 learning_gap.answer 不受 resolved 约束——缺席即不动 ```

于是「退回未解」现在只需要发 {gap_id, resolved: 0}，前端没机会写错。 「作废」同理，不必再把答案三件套原样搬运一遍。

推翻一条自己写下的理由

0.6.0 选整块替换是有理由的，而且写在测试的 docstring 里：

> 部分更新分不清「没提到」和「想清空」，写错的 answered_by 就再也改不回空。

这条理由不成立。JSON 本来就分得清——k in payload 与 payload.get(k) 是 两件事，0.6.0 只是没用上前者。test_explicit_null_still_clears 就是为回答它 而写的：显式传 null 照样把字段清回空。

app.js 有了第一把测试锁

躲不掉的那部分组装逻辑——「改解决方式」的撤销仍需回传整块并夹紧，因为 learning_gap 没有 CHECK 把 resolved 与 resolution 绑住，import.py 写得出写端点自己不收的行——抽进了 static/todo_payload.js，用 node 内建的 node:test 锁住：

``bash node --test apps/hvac_log/tests/js/*.test.js ``

零 npm 包、没有 package.json、没有 node_modules。 这个文件里一行都不碰 DOM，浏览器按普通 <script> 加载、node 按 CJS require 加载，两边共用同一份 ——测的就是页面真正跑的那份代码。应用本身跑起来一点都不需要 node。

新语义带来一个旧语义下不存在的新陷阱：JSON.stringify 会丢掉值为 undefined 的键，而丢键现在意味着「不动这一列」，不再是「清空」。四条锁专门盯着它。
