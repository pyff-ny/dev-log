fix(dev-log): 忽略事后补记的 status 翻转，修正发布时间派生

PR-264 · 更新: 2026-09-06T01:57:02-04:00

事故

2026-09-06 手动跑 reconcile-dev-log-sync.yml -f mode=repair，把 92 个 dev-log 页面全量重渲，结果 46 个 Case 的时间戳塌缩到同一点 2026-08-26T12:44:09，历史时间线失去先后顺序。

根因

resolve_release_timestamp() 找的是「把 frontmatter status 翻成 released 的 commit」。这在正常发布里是对的，但对 2026-08-26 之前发布的 Case，那次翻转发生在批量补数据的 commit：

`` b4f9cde docs: backfill release-notes.md status/updated from case.md (CASE-2026-089) 触及 75 个 release-notes.md ``

函数忠实返回了 backfill 时间，而那不是发布时间。

修法

trust_git_timestamp()：git 时间戳比 frontmatter 自身的值晚超过 24 小时时丢弃，回退 frontmatter。

判定是方向性的，不是纯量级 —— 补记天然发生在事后：

| 情形 | 判定 | 理由 | |---|---|---| | git 晚于 frontmatter >24h | 丢弃 git | 翻转是事后补记，frontmatter 更接近真相 | | git 早于 frontmatter | 保留 git | frontmatter 的 updated 被后续无关编辑动过，git 才是发布信号 | | 差值 ≤24h | 保留 git | 正常发布，git 秒级更精确 |

第二行正是 git 派生方案当初要解决的问题，由既有测试 test_sync_prefers_git_derived_timestamp_over_frontmatter 锁住 —— 纯量级阈值会打破它。

阈值依据

对本仓库 102 个真实 Case 实测，两侧分得很干净，中间是空的：

| Δ（git − frontmatter） | Case 数 | |---|---:| | ≤ 1 小时 | 43 | | 1–24 小时 | 4 | | 晚 95–425 小时 | 50（全部是 b4f9cde） | | 早 >24 小时 | 0 |

22.9h 和 95h 之间没有任何样本，24 小时落在断崖正中。

另一个被排除的方案：只跟 released_at 比。实测只有 6 个 Case 有 released_at，且没有一个漂移 >24h —— 50 个坏值全部只有 updated，那样一个都抓不到。
