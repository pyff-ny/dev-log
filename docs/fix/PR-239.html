fix(mk_hub): serve registry 保存加乐观并发控制

PR-239 · 更新: 2026-08-31T13:29:58-04:00

背景

2026-08-31 事故：john_wick_arsenal 的注册行在 mk_hub「mk serve registry」tab 保存后消失。根因调查（见下）证明那次事故是用户手工从备份覆盖注册表所致，与 mk_hub 无关；但调查过程中发现一个真实的丢失更新缺口：

  • GET /api/serve-registry 返回 mtime，但从未被前端保存、也从未被后端在保存时校验。
  • 外部追加行 → 保留（既有的逐行 passthrough 逻辑）
  • 外部删除 serve 行 → 400（既有的 missing 校验）
  • 外部修改已有 serve 行的字段（端口/路径/status/summary）→ 被 tab 加载时的陈旧快照静默覆盖

修复

  • GET /api/serve-registry 新增 revision（整份文件的 sha256，每次请求现算，不缓存不落盘）。
  • PUT /api/serve-registry 新增必填 revision；缺失 → 400；与磁盘当前值不符 → 409 + conflict:true，校验在生成备份之前，冲突时不产生备份、不产生临时文件、注册表零改动。
  • 前端保存后都会记住最新 revision；收到 409 时用响应里的最新 rows 重渲染列表并弹出可读提示，不静默失败、不静默覆盖。
  • 用 sha256 而非 mtime+size：本次事故的覆盖恰好是等长内容，size 比对发现不了。
  • 未做字段级三方合并——注册表是 mk serve 的 SSOT，宁可拒绝、不做猜测；升级后未刷新的旧页面保存会得到 400，属预期。

兼容性

  • GET 响应新增字段，additive。
  • PUT 请求新增必填字段，破坏性：前后端同一个 PR 一起发布。
  • save_serve_registry() 新增关键字参数 expected_revision=None，默认跳过校验，保留既有直接调用方行为。
  • mk_hub 是常驻 HTTP 服务，非 mk CLI 子命令，Exit Code Constitution 不适用；mk serve 全链路只读该文件，人类输出/JSON schema 零变化。
