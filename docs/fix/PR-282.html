fix(hvac-log): component_install 按当天工单归属，不再重复插入

PR-282 · 更新: 2026-09-09T21:47:16-04:00

问题

component_install.install_date 是事件日期——今天的复盘可以补录一次历史更换， schema 也允许它为空或为别的日子。但 write_all() 的 DELETE 一直拿它当导入日期用：

``python INSERT ... c.get("install_date") or day # 事件日期 DELETE FROM component_install WHERE install_date = ? # (day,) ← 当导入日期用 ``

两个日期一旦不同，那行永远删不掉又会被重插，每导一次同一天就多一行。

复现（install_date=2026-08-01，session_date=2026-09-05）：

`` 第1次: component_install = 1 第2次: component_install = 2 ← 应为 1 第3次: component_install = 3 ``

真实库目前 2 行、均有 job_id、install_date 都等于各自 session_date， 没有已产生的重复——这是潜伏缺陷，不需要数据修复。

改法

表里没有 provenance 列，但不必加：job.job_date 就是 session_date，而 job_date 是 job upsert 键的一部分、从不变更，所以 component_install.job_id 永远指向写它 那次导入当天的 job。job_id IN (当天的 job) 就是精确的「这次导入写的行」。

``python COMPONENT_INSTALL_OWNED = ( "install_date = ? OR job_id IN (SELECT job_id FROM job WHERE job_date = ?)") ``

- write_all() 的 DELETE 与预览的 day_snapshot() 共用同一份谓词， 避免读写漂移导致预览重新算错（这正是 #279 复审留下的那条风险） - REPLACEABLE_OWNED 改存 (谓词, 参数个数)，不再靠数问号推参数 - 两条都不沾的条目（无可解析 job_seq 且 install_date 不是当天）仍无法幂等， 改为逐条告警，写入路径与 --dry-run 共用同一句措辞

不改 schema、不写 migration、不动 VERSION。

归属安全性核对

加宽 DELETE 是本次最高风险处，逐条核过：

- 语句顺序：job upsert → ref["jobs"] 重解析 → DELETE → INSERT ✓ - 跨天误删：09-05 写的行 job_id 指向 09-05 的 job，导 09-08 时不匹配 ✓ - provenance 不漂：job_date 是 upsert 键的一部分，永不变更 ✓ - 第二写入口：serve.py 不写此表（只写 work_day / work_segment / segment_system / comp_period / question / learning_gap）， 无 0.4.0/0.6.0 那类「网页记的被复盘冲掉」路径 ✓

验证

- pytest apps/hvac_log/tests/ — 基线 270 passed，改后 272 passed - 新增 test_explicit_install_date_stays_idempotent、 test_unownable_install_warns_and_preview_tells_the_truth - 手工：历史补录连导 4 次，行数恒为 1 - 手工：两日库 14/14 张表预览仍等于实况（#279 的回归锁未被破坏）

已知残留

无 job_seq 的历史补录目前是死路：告警让人补 job_seq，但如果那天本来就没有工单， 用户补不了，行仍会每次多一份。这是本方案固有的边界——真正的解是给表加 provenance 列 （需要 migration，属 F3）。样例和真实库都不存在这种条目，暂为理论缺口。
